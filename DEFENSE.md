# Защита проекта split-expense-app

Учебное приложение для дележа общих расходов на Ruby on Rails 7.2 + SQLite.
Это обычный серверный Rails-монолит: HTML-страницы собираются на сервере из ERB-шаблонов, вход работает через сессию в cookie.

## Подготовка (один раз)

Все команды выполняются в Git Bash в папке проекта.

```bash
chcp.com 65001                  # обязательно: в пути к проекту кириллица, без этого bin/rails не запустится
bundle install                  # установить гемы
ruby bin/rails db:migrate       # создать таблицы
ruby bin/rails db:seed          # демо-данные: demo@example.com / secret123
ruby bin/rails db:test:prepare  # подготовить отдельную тестовую базу
```

- Запуск сервера: `ruby bin/rails server`, затем открыть http://localhost:3000
- Запуск тестов: `ruby bin/rails test` (с названиями тестов: `ruby bin/rails test -v`)

> После каждой новой миграции нужно заново выполнить `ruby bin/rails db:test:prepare`.
> На Linux и macOS Rails делает это сам, а на Windows автоматический вызов не срабатывает, и тесты пишут «Migrations are pending».

## Точка 1. Авторизация и регистрация на сессиях

### Что сделано

- Приложение переведено из режима API в обычный: из `config/application.rb` убрана строка `config.api_only = true`. Без неё Rails сам подключает cookies, сессии, flash-сообщения и защиту от CSRF.
- `ApplicationController` теперь наследуется от `ActionController::Base` (раньше был `ActionController::API`), поэтому умеет показывать ERB-шаблоны с общим layout.
- JWT убран полностью: гем `jwt`, `app/services/json_web_token.rb`, `AuthController` и пустой `config/initializers/cors.rb`.
- Модель `User` осталась прежней: `has_secure_password` (bcrypt), email обязателен и уникален, пароль от 6 символов.

| Файл | За что отвечает |
|---|---|
| `config/routes.rb` | связывает адреса с контроллерами |
| `app/controllers/application_controller.rb` | `current_user` (кто вошёл) и `require_login` (не пускать без входа) |
| `app/controllers/users_controller.rb` | регистрация: показать форму, создать пользователя, сразу войти |
| `app/controllers/sessions_controller.rb` | вход (проверка пароля → `session[:user_id]`) и выход (`reset_session`) |
| `app/controllers/profiles_controller.rb` | защищённая страница: `before_action :require_login` |
| `app/controllers/home_controller.rb` | главная страница |
| `app/views/layouts/application.html.erb` | общий каркас: шапка, flash-сообщения, место для страницы (`yield`) |
| `app/views/home`, `users`, `sessions`, `profiles` | ERB-шаблоны страниц |
| `config/locales/ru.yml` | русские тексты ошибок («Email: уже используется») |

Как работает вход:

1. Форма входа отправляет `POST /login` с email и паролем.
2. `User.find_by(email: ...)` ищет пользователя, `authenticate` сверяет пароль с bcrypt-хешем.
3. Если пароль верный, выполняется `session[:user_id] = user.id`. Rails сохраняет сессию в зашифрованную cookie `_split_expense_app_session`.
4. Браузер сам отправляет эту cookie с каждым запросом, поэтому после обновления страницы пользователь остаётся в аккаунте.
5. `current_user` берёт `user_id` из сессии и находит пользователя.
6. Кнопка «Выйти» вызывает `reset_session`: сессия очищается, `current_user` становится `nil`.

### Как запустить

`ruby bin/rails server`, затем открыть http://localhost:3000

### Что показывать

1. Главная без входа: «Вы не вошли» и кнопки «Войти» / «Регистрация».
2. Открыть http://localhost:3000/profile без входа: перекидывает на `/login` с сообщением «Сначала войдите».
3. Регистрация с пустыми полями: «Email: обязательное поле» и «Пароль: минимум 6 символов», поля подсвечены красным. Затем с уже занятым email: «Email: уже используется».
4. Успешная регистрация: на главной «Вы вошли как …» и кнопка «Выйти».
5. Нажать F5 несколько раз: пользователь остаётся в аккаунте. В F12 → Application → Cookies видна cookie `_split_expense_app_session`.
6. Открыть «Профиль»: теперь пускает.
7. «Выйти» → «Вы вышли», `/profile` снова перекидывает на вход.
8. Вход с неверным паролем: «Неверный email или пароль». С верным: «Вы вошли».
9. По желанию:
   - `ruby bin/rails middleware`: в списке есть `ActionDispatch::Cookies`, `ActionDispatch::Session::CookieStore`, `ActionDispatch::Flash`, то есть режим API выключен.
   - В консоли (`ruby bin/rails console`) выполнить `User.last.password_digest`: в базе лежит хеш вида `$2a$12$...`, а не пароль.

### Вопросы и ответы

1. **Как хранится пароль?**
   Самого пароля в базе нет, только bcrypt-хеш в колонке `password_digest` (это делает `has_secure_password`). Хеш нельзя превратить обратно в пароль. При входе `authenticate` хеширует введённый пароль с той же «солью», которая хранится внутри хеша, и сравнивает результаты.

2. **Где хранится сессия, почему её нельзя подделать и почему пользователя не выкидывает при обновлении страницы?**
   Сессия хранится в cookie браузера `_split_expense_app_session`. Rails шифрует и подписывает её секретом `secret_key_base`, который лежит в зашифрованном `config/credentials.yml.enc`; ключ к нему `config/master.key` в git не попадает. Поменять `user_id` внутри cookie нельзя: подделанная cookie не пройдёт проверку и будет проигнорирована. Флаг `HttpOnly` не даёт JavaScript прочитать cookie. Браузер прикладывает её к каждому запросу, а `current_user` каждый раз заново находит пользователя, поэтому F5 ничего не ломает. У cookie нет срока годности, и она живёт, пока открыт браузер.

3. **Как работают `current_user` и `before_action :require_login`?**
   `current_user` ищет пользователя по `session[:user_id]`. `||=` запоминает результат, чтобы за один запрос не ходить в базу несколько раз. `helper_method` делает метод доступным во вьюхах. `before_action` вызывает `require_login` перед действием контроллера: если пользователя нет, выполняется `redirect_to login_path`, и само действие уже не запускается.

4. **Чем сессии отличаются от JWT, который был раньше?**
   С JWT клиент сам хранил токен и отправлял его в заголовке `Authorization`. Сервер ничего не помнил, и «выйти» означало удалить токен на клиенте. С сессией браузер всё делает сам через cookie, а выход происходит на сервере (`reset_session`). Для сайта с ERB-страницами сессии — штатный и самый простой способ. JWT удобен для API, к которому обращается отдельный фронтенд или мобильное приложение.

5. **Что такое CSRF и как от него защищено приложение? Почему «Выйти» — кнопка, а не ссылка?**
   CSRF — это атака, при которой чужой сайт отправляет форму от имени вошедшего пользователя: браузер сам приложит его cookie. `ActionController::Base` проверяет секретный `authenticity_token`, а `form_with` и `button_to` сами добавляют его скрытым полем. Запрос без токена получает ошибку 422. Выход меняет состояние, поэтому это не GET-ссылка, а запрос DELETE. `button_to` создаёт форму с POST и скрытым полем `_method=delete`, и Rails (middleware `Rack::MethodOverride`) превращает такой запрос в DELETE.

## Точка 2. Модели и автотесты

### Что сделано

Схема данных:

```
users ──< participants ──< expenses
владелец   участники группы   траты (participant_id = кто заплатил)
```

- `User`: `has_many :participants`, `has_many :expenses, through: :participants`.
- `Participant`: `belongs_to :user`, `has_many :expenses` (траты, где он плательщик); имя обязательно.
- `Expense`: `belongs_to :participant`; название обязательно, сумма обязательна и больше нуля.
- Правило дележа: каждая трата делится поровну между всеми участниками пользователя.
- `User#balances` считает баланс каждого участника: сколько заплатил минус его доля. Возвращает `{ участник => баланс }`. Плюс — участнику должны, минус — он должен.
- `User#settlement` возвращает список переводов `{ from: кто, to: кому, amount: сколько }`.

| Файл | За что отвечает |
|---|---|
| `db/migrate/20261013100000_create_participants.rb` | таблица участников: `user_id` (внешний ключ), `name` |
| `db/migrate/20261013100100_create_expenses.rb` | таблица трат: `participant_id` (плательщик), `title`, `amount` типа `decimal(10, 2)` |
| `db/schema.rb` | итоговая схема базы, генерируется автоматически |
| `app/models/participant.rb`, `app/models/expense.rb` | связи и валидации |
| `app/models/user.rb` | связи и методы `balances` и `settlement` |
| `test/models/user_test.rb` | валидации User, `balances`, `settlement` (8 тестов) |
| `test/models/expense_test.rb` | валидации и связи Expense (6 тестов) |
| `test/models/participant_test.rb` | валидация имени и связи (3 теста) |
| `db/seeds.rb` | демо-данные для показа |

Пример расчёта на демо-данных:

| Участник | Заплатил | Доля (1800 / 3) | Баланс |
|---|---|---|---|
| Аня | 900 + 600 = 1500 | 600 | +900 |
| Боря | 300 | 600 | −300 |
| Вера | 0 | 600 | −600 |

Жадный алгоритм `settlement` по шагам:

1. Должники: Вера 600, Боря 300. Кредиторы: Аня 900.
2. Крупнейший должник Вера платит крупнейшему кредитору Ане меньшую из сумм: min(600, 900) = 600. Вера в нуле и выбывает, Ане ещё должны 300.
3. Боря платит Ане min(300, 300) = 300. Оба в нуле.
4. Должников не осталось. Итог: «Вера → Аня 600», «Боря → Аня 300».

### Как запустить

```bash
ruby bin/rails db:migrate
ruby bin/rails db:test:prepare
ruby bin/rails test -v
```

Ожидаемый итог: `17 runs, 40 assertions, 0 failures, 0 errors, 0 skips`.

### Что показывать

1. `ruby bin/rails test -v`: все 17 тестов зелёные, видны их названия.
2. Открыть `test/models/user_test.rb` и пройтись по тестам `settlement`: двое → один перевод; трое, заплатил один → два перевода; все в нуле → переводов нет; смешанный случай с порядком переводов.
3. По желанию показать, что тесты ловят ошибку: в `settlement` заменить `debtors.max_by` на `debtors.min_by`. Тест «biggest debtor pays biggest creditor first» станет красным. Потом вернуть как было.
4. Консоль `ruby bin/rails console`:

```ruby
user = User.find_by(email: "demo@example.com")
user.participants.pluck(:name)   # => ["Аня", "Боря", "Вера"]
user.expenses.sum(:amount).to_f  # => 1800.0
user.balances.map { |participant, balance| [ participant.name, balance.to_f ] }
# => [["Аня", 900.0], ["Боря", -300.0], ["Вера", -600.0]]
user.settlement.map { |t| "#{t[:from].name} -> #{t[:to].name}: #{t[:amount].to_f}" }
# => ["Вера -> Аня: 600.0", "Боря -> Аня: 300.0"]

e = Expense.new(title: "", amount: 0)
e.valid?                # => false
e.errors.full_messages  # => ["Плательщик: не указан", "Название: обязательное поле", "Сумма: значение должно быть больше 0"]
```

`.to_f` нужен только для красивого вывода: без него консоль печатает `BigDecimal` в виде `0.9e3`, то есть 900.

### Вопросы и ответы

1. **Что в миграциях и почему `amount` — `decimal`, а не `float`?**
   Две таблицы: `participants` (`user_id`, `name`) и `expenses` (`participant_id`, `title`, `amount`). `t.references ... foreign_key: true` создаёт колонку, индекс и внешний ключ, а `null: false` запрещает пустые значения уже на уровне базы. `float` хранит числа приближённо (в Ruby `0.1 + 0.2` даёт `0.30000000000000004`), для денег это недопустимо. `decimal(10, 2)` хранит ровно два знака после запятой, и в Ruby значение приходит как точный `BigDecimal`.

2. **Как считается баланс?**
   Каждая трата делится поровну на всех участников, поэтому доля каждого = (сумма всех трат) / (число участников). Баланс = сколько заплатил − доля. Сумма балансов всех участников равна нулю: сколько одни переплатили, столько другие недоплатили. Баланс округляется до копеек, поэтому при делении на 3 может «потеряться» копейка: 100 ₽ на троих дают +66.67, −33.33, −33.33.

3. **Как работает `settlement`, почему цикл не бесконечный и даёт ли он минимум переводов?**
   Участники делятся на должников (баланс меньше нуля) и кредиторов (больше нуля). Пока есть и те и другие, берём крупнейшего должника и крупнейшего кредитора, переводим меньшую из двух сумм и вычитаем её у обоих. Хотя бы один из них становится ровно нулём и выбывает, поэтому цикл конечен, а переводов не больше n − 1.
   *Подвох:* жадный алгоритм не всегда даёт абсолютный минимум. Для балансов +7, +6, −6, −4, −3 он сделает 4 перевода, хотя можно обойтись тремя: −6 → +6, а −4 и −3 → +7. Точный минимум требует перебора групп участников и очень медленный на больших группах, поэтому жадный способ — разумный компромисс: просто, быстро и не больше n − 1 переводов.

4. **Зачем `has_many :through` и почему нет таблицы «кто с кем делит»?**
   `has_many :expenses, through: :participants` получает все траты пользователя одним SQL-запросом с JOIN через `participants`, поэтому в таблице `expenses` не нужен `user_id`. Отдельная join-таблица понадобилась бы, если бы трату делили не все участники. По условию делят все, поэтому хватает связи «трата → плательщик». Минус такого решения: нельзя исключить участника из конкретной траты.

5. **Как устроены тесты?**
   Используется встроенный в Rails Minitest. Три файла в `test/models`: валидации и связи каждой модели, плюс `balances` и `settlement` в разных сценариях. Данные создаются прямо в тесте (`@user.participants.create!(...)`), чтобы сразу было видно, что проверяется. Каждый тест выполняется в транзакции, которая в конце откатывается, поэтому тесты не мешают друг другу. Тестовая база отдельная: `storage/test.sqlite3`.

### Вопросы и ответы

1. **Почему CSS в папке `public`, а не в `app/assets`?**
   Приложение создавалось как API, поэтому asset pipeline (Sprockets или Propshaft) в нём не подключён. Чтобы не добавлять гем, файл лежит в `public`: Rails отдаёт эту папку как есть, и CSS подключается обычным `<link rel="stylesheet" href="/styles.css">`. Минус — в имени файла нет версии, поэтому браузер может показать старую копию из кэша (лечится Ctrl+F5).

2. **Зачем CSS-переменные?**
   Цвета и радиус скругления заданы один раз в `:root` (например, `--accent: #0d9488`) и используются через `var(--accent)`. Чтобы сменить цвет на всём сайте, достаточно поменять одну строку.

3. **Почему без Bootstrap или Tailwind?**
   Так требовало задание. К тому же проекту нужен примерно десяток компонентов: их проще написать самому, чем подключать фреймворк. Каждый класс в файле понятен, и лишних зависимостей нет.

4. **Как подсвечивается поле с ошибкой?**
   Если у модели есть ошибка в поле, `form_with` сам оборачивает подпись и поле ввода в `<div class="field_with_errors">`. В CSS для этого класса заданы красная рамка и красная подпись, больше ничего делать не нужно.

5. **Зачем нужна витрина и почему она статическая? Как вёрстка подстраивается под телефон?**
   Витрина — это справочник компонентов: все элементы и их состояния (обычное, неактивное, с ошибкой) видны на одной странице, а новые страницы собираются из готовых классов. Она показывает внешний вид, а не логику, поэтому форма траты на ней — образец и данные никуда не отправляет. Под телефон: в layout есть `<meta name="viewport">`, ширина контейнера ограничена `max-width`, а ряды кнопок и цветов переносятся на новую строку благодаря `flex-wrap`.
